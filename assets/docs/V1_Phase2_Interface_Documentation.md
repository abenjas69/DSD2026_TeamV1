## 2. Phase II Context

Phase II focuses on standard rehabilitation movement curves and comparison with patient/session movement data. The current supported movements are:

- walking
- squat
- upstairs / stair climbing

The standard curves are already generated locally using V1 scripts. For the first deployable recommendation version, V1 is not using image input. Lee confirmed that raw or processed motion data input is acceptable and preferred for this stage.

The current recommendation module compares patient/session curve data with local standard curve CSV data. It generates JSON and TXT outputs containing engineering metrics, status labels, observations, and cautious doctor-review notes.

Image input may be considered later, but it is not the current deployment path. The current output is AI-assisted/rule-based support for review and must not be treated as a clinical diagnosis.

## 3. V1 Responsibilities in Phase II

V1 is responsible for:

- generating or maintaining standard movement curves;
- comparing patient/session curves with standard curves;
- calculating comparison metrics;
- generating recommendation outputs;
- providing JSON/TXT outputs to web/backend teams;
- supporting visualization and validation through generated HTML/CSV outputs.

V1 is not responsible for:

- doctor-patient binding;
- account management;
- final clinical diagnosis;
- frontend chart rendering;
- database ownership;
- sensor hardware connection.

### 4.4 generate_recommendation_from_curves.py

Purpose: compare patient/session movement curve data with a local standard curve and generate recommendation outputs.

The current script:

- compares patient/session data with standard curve data;
- calculates curve comparison metrics;
- supports `walking`, `squat`, and `upstairs`;
- supports local patient CSV input;
- supports patient session API input through `--patient-session-id`;
- outputs JSON and TXT recommendation files;
- can optionally output HTML and CSV validation artifacts if those CLI paths are provided.

The current implementation is rule-based and AI-assisted in the sense that it converts motion-analysis metrics into structured recommendation support. It does not currently call a remote LLM API during recommendation generation.

## 5. Input Interfaces to V1

### 5.1 Standard Curve Files

Standard curve CSV files are local inputs for the recommendation module.

Expected or supported columns include:

- `percent`
- `mean_angle`
- `smooth_angle`
- `sd_angle`
- `mean_minus_sd`
- `mean_plus_sd`

The script prefers `smooth_angle` as the standard curve value when available. It may also use `standard_angle`, `mean_angle`, or `angle` as fallback columns depending on the CSV file.

The standard deviation band, when available, can be used to estimate how much of the patient movement falls outside the healthy baseline range. This is an engineering comparison and is not clinically validated by itself.

### 5.2 Patient Curve CSV Input

Patient/session data may be passed as a CSV file with `--patient-csv`.

Supported flexible columns may include:

- `percent` plus `angle`
- `percent` plus `patient_angle`
- `time_seconds` plus `angle`
- `time_seconds` plus `patient_angle`
- `time_seconds` plus `standard_angle`, if applicable

The current script also accepts related time columns such as `cycle_time_seconds` and `repetition_time_seconds` when present.

V1 normalizes patient curves to a 0-100% movement progress grid before comparison with the standard curve.

### 5.3 Patient Session API Input

Patient session API input is implemented in `generate_recommendation_from_curves.py`.

- Base URL: `http://113.44.220.94:3000/measurements`
- CLI argument: `--patient-session-id`
- Angle argument: `--angle-id`
- Default angle ID: `left_knee`
- API endpoint used by the script: `{base_url}/{patient-session-id}`
- Expected field: `joint_angles`
- Expected angle field: `angleID`
- Expected angle value by default: `left_knee`

The script expects measurement records that contain timestamped joint-angle values. For each record, it reads `joint_angles`, filters by `angleID`, and uses the corresponding `angle` values to build the patient curve.

### 5.4 Action Type Input

Allowed action values:

- `walking`
- `squat`
- `upstairs`

The action affects interpretation, recommendation text, and segmentation behavior.

### 5.5 Angle ID Input

Default:

- `left_knee`

Other angle IDs may be supported later if S1/S2 provide consistent data for them and the standard curves are generated for those angles.

## 7. Metrics Provided by V1

- `patientPeakAngle`: maximum patient angle in the normalized movement curve.
- `standardPeakAngle`: maximum standard/reference angle.
- `peakAngleDifference`: difference between patient and standard peak angle.
- `patientMinAngle`: minimum patient angle in the normalized movement curve.
- `standardMinAngle`: minimum standard/reference angle.
- `minAngleDifference`: difference between patient and standard minimum angle.
- `patientAmplitude`: patient movement range, calculated as peak angle minus minimum angle.
- `standardAmplitude`: standard movement range.
- `amplitudeDifference`: difference between patient and standard amplitude.
- `amplitudeRatio`: patient amplitude divided by standard amplitude, when calculable.
- `rangeOfMotionPercentOfStandard`: patient range of motion as a percentage of the standard range.
- `MAE`: mean absolute error between patient and standard curves.
- `RMSE`: root mean square error between patient and standard curves.
- `shapeRmseAfterOffsetCorrection`: shape difference after removing average vertical offset.
- `maxAbsoluteDeviation`: largest absolute curve difference at any normalized point.
- `meanSignedDeviation`: average signed difference; negative values can indicate the patient curve is generally below the standard curve.
- `correlation`: similarity of the patient and standard curve shapes.
- `outsideStandardBandPercent`: percentage of patient curve points outside the standard deviation band, when the band exists.

These metrics help doctors and web/backend teams understand where the patient movement differs from the standard reference. They should be interpreted cautiously and reviewed by a qualified clinician.

## 8. Recommendation Status

Possible statuses:

- `normal`
- `mild_deviation`
- `significant_deviation`
- `unclear`

The thresholds are preliminary engineering thresholds. They are useful for software testing and early decision support, but they must not be interpreted as clinically validated thresholds.

## 9. Interface with Other Teams

S1 provides:

- healthy-person motion data;
- patient motion sessions;
- action acquisition protocols;
- movement labels if available.

V1 needs from S1:

- correct action labels;
- session IDs;

S2 provides:

V1 needs from S2:

- stable measurement API format;
- `joint_angles` field;
- `angleID` consistency;

- comparison metrics;

M2 displays:

- patient curve vs standard curve;

- JSON recommendation;

M1 may use:

## 13. Limitations

- Recommendation thresholds are preliminary.
- Outputs are not a medical diagnosis.
- Results depend on the quality, consistency, and labeling of the input data.
- `left_knee` is currently the main angle used by V1.
- More clinical validation is needed.
- Standard curves may need more healthy participants.
- Integration paths may change depending on M2/V2 deployment.
- The current recommendation logic is rule-based and does not replace clinical judgement.

## 14. Future Work

- Add accuracy evaluation once labeled data is available, for example `good` / `ill` or more detailed labels such as mild/severe knee or ankle injury.
